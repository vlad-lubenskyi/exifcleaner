# Migrating ExifCleaner from Electron to MōBrowser

This document records how ExifCleaner 4.7.0 (Electron 44, electron-vite, electron-builder) was
ported to MōBrowser 2.19.0, what changed and why, how it was verified, and what is still missing.
The Electron app at the repository root is untouched and remains the shipping product; this
directory is a separate, self-contained MōBrowser project.

## 1. Approach

- **New project next to the old one.** `mobrowser/` was generated with the official scaffolder
  (`npm create mobrowser-app@latest -- --name ExifCleaner --native no --git no --dir .`) and
  committed unmodified. The ExifCleaner sources were then copied in verbatim and committed
  unmodified as a second step, so every later diff is the porting work and nothing else.
- **Follow MōBrowser's layout instead of reconfiguring it.** Files were moved into the
  directories MōBrowser expects (`src/main`, `src/renderer`, `src/renderer/proto`, `resources/`,
  `assets/`) rather than pointing the build at the old paths.
- **Change the build and the IPC; leave everything else alone.** The domain, application,
  ExifTool and metadata layers are byte-identical to the Electron app apart from import paths.
  The React renderer changed in two lines plus import paths: it still calls `window.api.*`, and
  a new renderer module rebuilds `window.api` on top of MōBrowser's generated IPC clients.

## 2. Commit history

| Commit | What it does |
| --- | --- |
| `chore(mobrowser): scaffold …` | Unmodified `create-mobrowser-app` output. |
| `chore(mobrowser): copy ExifCleaner sources …` | Verbatim copies into the new layout; removes the template's demo app. Does not build. |
| `feat(mobrowser): port ExifCleaner …` | Build config, IPC contract, main-process port, renderer adapter, resources, tests, docs. |

```
│   │   ├── common/            ← src/common/**          (unchanged)
│   │   ├── infrastructure/    ← src/infrastructure/**  (unchanged except mobrowser/)
│   │   │   └── mobrowser/     ← src/infrastructure/electron/  (rewritten adapters)
│   │   ├── ipc/               ← src/main/ipc/  (schemas unchanged; validation, events, converters new)
│   │   └── gen/               generated by `npm run gen` (git-ignored)

│       │   └── window_api.ts  ← src/preload/index.ts   (rewritten, see §7)
│       ├── proto/*.proto      new: the IPC contract (see §5)
│       └── gen/               generated by `npm run gen` (git-ignored)
└── test/e2e/                  new MōBrowser e2e tests (see §10)
```

**Why `domain/`, `common/`, `application/` and `infrastructure/` moved under `src/main/`.**
MōBrowser has two source roots, one per process. These layers are owned by the main process; the
renderer only imports pure modules from them (`domain`, `common/types`, `common/ipc_channels`),
none of which touches Node.js. Renderer imports were rewritten mechanically
(`../../domain` → `../../main/domain`).

**Removed from the template:** the shadcn/Tailwind UI kit and its skill, the demo services
(app/menu/settings), demo tests, `components.json`, `postcss.config.js`, the template update flow,
and the nested `.github/workflows` (GitHub only runs workflows at the repository root).

**Not carried over:** `src/preload/` (MōBrowser has no preload), `src/main/security/crash_dumps.ts`
(Electron `crashReporter`, a CI-only diagnostic), `electron.vite.config.ts`, `scripts/afterPack.cjs`,
the root release/verification scripts and the Electron unit/e2e suites (they still run against the
root app).

## 4. Build system

| Electron | MōBrowser |
| --- | --- |
| `electron-vite` with three targets (main, preload, renderer) | `mobrowser` CLI running Vite 8 twice: `--mode main` and `--mode renderer`. No preload target. |
| `electron-builder` (`.dmg`, `.AppImage`, `.deb`, `.rpm`, NSIS, portable) | `npm run build` → `build/dist/<platform>-<arch>/bin`; `npm run pack` → `.dmg` (macOS) and a Velopack installer (Windows). |
| `package.json` `"build"` section | `mobrowser.conf.json` |
| `yarn` | `npm` (MōBrowser's toolchain and lockfile) |
| `tsc --noEmit` | `npm run typecheck` (`mobrowser gen && tsc --noEmit`) |
| — | `npm run gen`: Protobuf → TypeScript for both processes |

Commands:

```bash
npm install          # also runs scripts/prune_native_prebuilds.mjs (§8)
npm run dev          # app + Vite dev server with HMR
npm run typecheck
npm run lint         # Prettier, tabs (.prettierrc copied from the root)
npm run test:e2e     # builds the app and runs test/e2e
npm run build        # native executable for the current platform
npm run pack         # native installer for the current platform
```

### `vite.config.ts`

The template config, plus:

- **CSP plugin** carried over from `electron.vite.config.ts`, with one fix: in production the
  renderer is served from `mobrowser://app`, which Chromium does **not** match with `'self'`
  (custom scheme), so the origin is listed explicitly. Without it the bundled app is a blank
  window: the CSP blocks its own script and stylesheet. Dev mode loads from `http://localhost`, so
  it never shows the problem.
- **`exifcleaner-node` is external** to the main bundle (see §8).
- Dropped: `removeCrossOriginPlugin` (it worked around `file://` in packaged Electron; MōBrowser
  serves the renderer over its own scheme) and the template's update-server define.

### `tsconfig.json`

The original strictness flags (`strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`,
`noImplicitReturns`, …) on the template's structure. **`verbatimModuleSyntax` is off** because the
code MōBrowser generates into `src/main/gen/ipc_service.ts` imports types without `import type`,
and generated files can't be edited. Hand-written code still uses `import type` throughout.

### `mobrowser.conf.json`

- `app.name`, `version` (4.7.0), `author`, `copyright`, `description`, `bundleID` (`com.exifcleaner`).
- `app.locales`: every ExifCleaner language MōBrowser can localize its own UI in. MōBrowser labels
  role menu items (Copy, Quit, …) and DevTools in the system language from this list.
- `app.nodeModules: ["exifcleaner-node"]` (see §8).
- Per-platform `extras` for the ExifTool binaries (see §8).
- `executableName: "ExifCleaner"` on every platform, so the user-data directory doesn't depend on
  `app.name`.

## 5. IPC

### Model

| Electron | MōBrowser |
| --- | --- |
| Preload script exposes `window.api` via `contextBridge` | No preload. The renderer imports generated clients from `src/renderer/gen/ipc.ts`. |
| Channel names in `common/ipc_channels.ts` + hand-written TS types | `.proto` files in `src/renderer/proto/` are the contract; `npm run gen` writes both sides. |
| `ipcMain.handle` / `ipcRenderer.invoke` | `ipc.registerService(Descriptor, { Method })` / `await ipc.<file>.<Method>(msg)` |
| `ipcRenderer.send` (fire-and-forget) | Unary RPC the renderer does not await (`void …catch(console.error)`). |
| `webContents.send` (main → renderer) | Server-streaming RPC (`returns (stream X)`), registered without an implementation: `ipc.registerService(Descriptor)` returns one publish function per stream. |
| Sender allowlist (`event.sender.id`) | Built in: only trusted origins reach the bridge, and the frame origin is re-checked in the main process. |
| zod payload validation | Kept: `validated(schema, handler)` in `src/main/ipc/ipc_validation.ts` runs the unchanged `ipc_schemas.ts`. |

### Contract

One `.proto` per former `window.api` namespace, because each file that declares a service becomes
one `ipc.<file name>` client:

| `window.api` | Proto | Methods | Streams (main → renderer) |
| --- | --- | --- | --- |
| `exif` | `exif.proto` | `ReadMetadata`, `RemoveMetadata` | — |
| `files` | `files.proto` | `ChooseFiles`, `ChooseFolder`, `NotifyFilesAdded`, `NotifyFileProcessed`, `NotifyAllFilesProcessed` | `OnFileOpenAddFiles` |
| `folder` | `folder.proto` | `Classify`, `Expand` | — |
| `i18n` | `i18n.proto` | `GetLocale`, `GetStrings` | `OnLanguageChanged` |
| `reveal` | `reveal.proto` | `ShowInFolder`, `ShowContextMenu` | — |
| `settings` | `settings.proto` | `Get`, `Set` | `OnChanged`, `OnToggle` |
| `theme` | `theme.proto` | `Get`, `Set`, `GetAccentColor` | `OnChanged`, `OnAccentColorChanged`, `OnThemeModeChanged` |
| `platform.isMac` | — | `navigator.userAgent` in the renderer, as the MōBrowser template does | — |
| `files.basename`, `files.getPathForFile` | — | renderer-local (see §11) | — |

`common.proto` holds shared messages (`FilePath`, `PathList`, …) and declares no service.

### Mapping TypeScript types onto Protobuf

- **ExifTool metadata** (`Record<string, unknown>`) travels as `google.protobuf.Struct`, which the
  generator maps to `{ [key: string]: any }`.
- **`RemoveMetadataResult`** is a discriminated union of four shapes. It is flattened into one
  message (`success`, `failure_kind`, the union of fields). The main process flattens it
  (`toRemoveMetadataResultMessage` in `exif_handlers.ts`) and the renderer rebuilds the exact union
  (`fromRemoveMetadataResult` in `window_api.ts`), so `use_process_files.ts` is unchanged.
- **`Settings.language: string | null`**: proto3 has no null, so an absent `optional string language`
  means `null`. A partial update that sets the language back to "System" sends
  `follow_system_language = true` (`src/main/ipc/settings_message.ts`).
- **`I18nStringsDictionary`** (`key → locale → text`) is `map<string, LocalizedString>`.

### Where the code lives

- `src/main/ipc/events.ts`: the publish handles for the streams (replaces every
  `webContents.send`).
- `src/main/ipc/ipc_validation.ts`: `validated(schema, handler)`.
- `src/main/ipc/settings_message.ts`: settings ↔ message conversion.
- `src/main/*_handlers.ts`, `lifecycle/dock.ts`: one `ipc.registerService` per service. The
  handler bodies are the Electron ones. Only the registration wrapper changed.
- `src/renderer/api/window_api.ts`: the generated clients → `window.api`.

A service whose streams are runtime-owned is registered twice: once without an implementation
(`events.ts`, which returns the publishers) and once with its unary methods. MōBrowser supports
this pairing explicitly.

### Ordering

`index.ts` awaits `initProcess()`, which starts ExifTool, loads settings and registers every
service, **before** it creates the window, and the window is created with `url: app.url`. Two
reasons:

1. The renderer calls services during its first render; they must exist.
2. Creating the window first and calling `loadUrl` later swaps the renderer process, which closed
   the page Playwright had attached to (the first e2e run failed this way).

### Cost

Measured in the running app: 1,000 parallel `GetLocale` round trips take 13 ms; 200 sequential
take 9 ms (≈0.05 ms each). That is negligible next to ExifTool's per-file time, so the
"no per-file IPC overhead" rule holds.

## 7. Renderer

The renderer changed in two lines plus import paths:

1. `index.tsx`: `import "./api/window_api";` as the first line. It installs `window.api` before
   React renders, which is what the preload used to do.
2. `env.d.ts`: types `window.api` as `WindowApi` (the renamed `ElectronApi`) from `./api/api_types`.

Everything else is mechanical import rewriting (`../../domain` → `../../main/domain`). All
components, hooks, contexts, styles and `index.html` are the Electron app's.

`window_api.ts` is a thin adapter: it awaits the generated clients, unwraps messages
(`{ value }`, `{ paths }`, `{ tags }`), rebuilds `RemoveMetadataResult` and `Settings`, and turns
each server stream into the `(callback) => unsubscribe` shape of the old `ipcRenderer.on` wrappers.

## 8. Resources, ExifTool and the native dependency

### Runtime resources

MōBrowser copies `<project>/resources/` into the bundle as-is (`Contents/Resources` on macOS,
`resources/` on Windows and Linux), in development builds too, and
`app.getPath("appResources")` returns that directory. This replaces Electron's split between
`.resources/` in dev and `process.resourcesPath` in production. `resources/` holds
`strings.json`, `icon.png`, `check.png` and `nix/exiftool-config/watchdog.config`.

### ExifTool binaries

Electron shipped `nix/bin` only to macOS/Linux and `win/bin` only to Windows. Putting both trees
in `resources/` would add the 35 MB Windows Perl runtime to every macOS build and 20 MB of Unix
Perl to Windows. So they live in `assets/exiftool/{nix,win}/bin` and each platform's `extras`
copies only its own:

| Platform | `from` | `to` | Resolved by the unchanged `binaries.ts` as |
| --- | --- | --- | --- |
| macOS | `assets/exiftool/nix/bin/` | `Resources/nix/bin` (relative to `Contents`) | `<appResources>/nix/bin/exiftool` |
| Windows | `assets/exiftool/win/bin/` | `resources/win/bin` | `<appResources>\win\bin\exiftool.exe` |
| Linux | `assets/exiftool/nix/bin/` | `resources/nix/bin` | `<appResources>/nix/bin/exiftool` |

The macOS layout was verified in both the dev and the production bundle. The Windows and Linux
destinations follow the documented `appResources` location but were **not** built or run (see §11).

`update_exiftool.pl` still writes into the repository root's `.resources/`; copy the results into
`assets/exiftool/` afterwards.

### `exifcleaner-node` ships native code

`exifcleaner-node` (a production dependency of the Electron app as well) contains prebuilt N-API
add-ons, `prebuilds/<platform>-<arch>/publication.node`, which it loads with
`createRequire(import.meta.url)` relative to its own files. (`gypfile: false` only means nothing
compiles at install time.) The port needed three changes for it:

1. **Don't bundle it.** When Vite bundled it into `out/main/index.js`, the relative path broke and
   every verified write (JPEG, PNG, …) failed with "Couldn't write the cleaned output". It is now
   a Vite `external`. MōBrowser's CLI tries to externalize packages with native binaries
   automatically but misses this one (§12), and it merges a user `external` correctly only when
   that `external` is a function.
2. **Ship it unbundled.** `app.nodeModules: ["exifcleaner-node"]` copies the package to
   `<appResources>/app/node_modules/` next to the main bundle, where Node resolves the external
   import at runtime.
3. **Keep only the host's prebuild.** MōBrowser refuses a `nodeModules` package that contains a
   `.node` file for another architecture, and `exifcleaner-node` ships six in one package.
   `scripts/prune_native_prebuilds.mjs` runs on `postinstall` and deletes the others from
   `node_modules`. To build for another architecture, reinstall with `npm_config_arch=<arch>`
   (and `npm_config_platform`). The proper fix is upstream: publish per-platform optional packages
   from `exifcleaner-node`.

The installed `exifcleaner-node@0.4.0` has the same integrity hash as the root `yarn.lock`.

## 9. Security model

| Concern | Electron app | MōBrowser port |
| --- | --- | --- |
| Renderer isolation | `sandbox`, `contextIsolation`, `nodeIntegration: false` | Always on; not configurable |
| Bridge surface | Preload-exposed `window.api` | Generated clients for the declared services only |
| Who may call IPC | Sender `webContents.id` allowlist | Trusted-origin gate (`app.trustedOrigins` is empty: only the bundled app), re-checked in main |
| Payload validation | zod | Protobuf typing + the same zod schemas |
| Navigation / popups | Blocked except app content; HTTPS popups go to the system browser | Same, via `navigation`/`openPopup` handlers |
| Permissions | Deny by default (clipboard write allowed) | Same |
| CSP | `<meta>` injected by Vite | Same policy, plus the `mobrowser://app` origin in production |
| DevTools in production | Disabled | The View menu offers DevTools in development only |
| Env-var / CLI injection | Electron fuses (`runAsNode`, `NODE_OPTIONS`, `--inspect` off) | Built in: packaged apps ignore `NODE_OPTIONS` and similar variables, and Chromium switches |
| Code integrity | — | `app.bin` integrity trailer; tamper resistance requires signing |

The gap noted for the Electron app still applies: the main process trusts any non-empty path the
renderer sends to `RemoveMetadata`/`Expand`. Origin checks narrow who can send it; a path
allowlist would close it.

All on macOS (Apple Silicon), MōBrowser 2.19.0:

- `npm run typecheck`, `npm run lint`: clean.
- `npm run test:e2e` (production build, fresh profile per test): 3/3 passed, three runs in a row.
  1. The empty state renders the i18n strings fetched over IPC.
  2. A file chosen in the native open dialog is cleaned into a `_cleaned` copy.
  3. Choosing German in Settings relabels the window live.
- Driven in the dev app with `npm run -s agent`:
  - JPEG, PNG, PDF and MP4 through the full UI pipeline (Choose files… → native dialog → rows →
    "4 of 4 cleaned"). ExifTool confirms GPS, Make, Artist and Copyright are gone from the JPEG
    copy; the JPEG keeps only its resolution tags and the PNG only its structural header fields,
    which is what the default "preserve resolution" setting asks for.
  - 200 JPEGs read → remove → re-read in **2.13 s**, 200/200 successful.
  - Dark theme from Settings applies immediately and is persisted to `settings.json`.
  - A settings toggle persists to `settings.json` and streams back to the window.
  - Folder expand (recursive, unsupported files counted as skipped) and classify (file vs folder,
    sizes, empty paths dropped).
  - Reveal dialog: localized buttons, cancel path, "file no longer exists" path.
- Production bundle: `strings.json`, icons, `nix/bin/exiftool` + `lib/`, and

**Not verified:** Windows and Linux builds, the native menus (the automation can't click them),
the Dock badge, `npm run pack` (DMG/installer), and a code-signed build.

## 11. Known gaps and behavior changes

### Blocking

- **Dropping files into the window doesn't work.** MōBrowser 2.19 gives the renderer no way to get a
  dropped `File`'s absolute path: there is no `webUtils.getPathForFile` counterpart, `File` has only
  `name`/`size`/`webkitRelativePath` (empty), and the bridge exposes nothing but the RPC channel.
  This was confirmed by dropping real files through CDP. The drop zone still renders and accepts
  the drop, but nothing is added (`getPathForFile` returns `""`, which `folder.classify` skips with
  a warning). Choose files…, Choose folder… and File > Open all work. This needs a MōBrowser
  feature (a drop path API or a main-process drop handler) before the port can replace the Electron
  app.

### Not available in MōBrowser 2.19, dropped

- Taskbar/Dock progress bar (`setProgressBar`), Dock bounce, Windows frame flashing and the
  taskbar overlay checkmark. Batch progress is shown on the macOS Dock badge only.
- Windows jump-list task "Open file" (`app.setUserTasks`).
- macOS Services, Speech, Bring All to Front and window-list menu items.
- Native About panel: replaced by a message dialog.
- Context menu on demand: the save-as-copy reveal menu (right-click on the reveal icon) is now a
  native message dialog with "Reveal cleaned copy", "Reveal original" and "Cancel". The renderer
  cancels Chromium's own context-menu request for that icon, and MōBrowser can only show a native
  context menu in answer to one.
- Background color before first paint (Electron's `backgroundColor`): a dark-mode launch may flash.
- Linux `.AppImage`/`.deb`/`.rpm` and the Windows portable `.exe`: MōBrowser packs installers for
  macOS and Windows only.
- Crash-dump diagnostics (`crashReporter`, CI-only).
- Opening files from the OS ("Open With", a drop on the Dock icon, command-line paths): the
  Electron app didn't support them either. In MōBrowser they need `fileAssociations`, which would
  declare `.jpg` and the rest as ExifCleaner documents (icon and default-handler claims). Without
  them, `app.launchInfo.files` stays empty and command-line paths don't reach `process.argv`
  (tested).

### Behavior changes

- Role menu items (Copy, Select All, Hide, Quit, Minimize, Zoom, …) and the context menu are
  labelled by MōBrowser in the **system** language, not in the language chosen in ExifCleaner.
  Custom items (File > Open…, Settings…, Appearance, Language, Help) still follow the app language.
- Developer Tools appears in the View menu in development only. Packaged Electron builds showed the
  item, but it did nothing.
- On macOS, Settings… (⌘,) lives only in the app menu. The File menu copy has no shortcut there,
  to avoid two items with one shortcut.
- The saved appearance (`themeMode` in `settings.json`) is applied at startup; MōBrowser also
  remembers `app.theme` itself.
- The user-data directory is `~/Library/Application Support/com.exifcleaner.ExifCleaner` (macOS),
  so settings and window state from the Electron app are not picked up.
- Bundle size: the macOS `.app` is 375 MB uncompressed, of which 345 MB is MōBrowser's Chromium
  framework; the app itself (resources, ExifTool, `app.bin`) is about 30 MB.

### Other

- Unconfirmed visual glitch: during one automation session, a white strip appeared above the
  Settings drawer's language field in dark mode. The DOM had nothing white at that spot, and later
  screenshots proved stale (they ignored a scroll change), so it may be a screenshot artifact.
  Check it by hand.
- `npm audit` reports GHSA-mrhx-c7xc-m3w5 in zod 3.x. The Electron app uses the same `^3.25.0`
  range; the fix is zod 4, a breaking upgrade for both.

## 12. Issues found in MōBrowser

Worth reporting to TeamDev:

1. **No absolute path for dropped files** (§11, blocking for ExifCleaner).
2. **Auto-externalization misses packages whose `exports` map hides `package.json`.** The CLI's
   native-binary probe calls `require.resolve("<pkg>/package.json")`, which throws for
   `exifcleaner-node`, so the package is bundled and its add-on can't be found.
3. **A user `rollupOptions.external` array breaks the build.** The CLI merges its function with the
   user's array into `[…, Function]`, which Rolldown rejects ("Expected (string | RegExp) but
   received Function"). A function works.
4. **`nodeModules` rejects packages that ship prebuilds for several architectures**, the common
   `prebuilds/<platform>-<arch>/` layout.
5. **`'self'` in a CSP `<meta>` doesn't cover `mobrowser://app`**, so a strict CSP that works in
   `npm run dev` blanks the packaged app. Worth a note in the docs.
6. **Generated `ipc_service.ts` isn't compatible with `verbatimModuleSyntax`** (types imported
   without `import type`).
7. No `will-quit`/before-quit event, no programmatic context-menu popup, no radio menu items.

## 13. Working on this project

- Edit a `.proto` → `npm run gen` → implement the method in the main-process handler → expose it
  in `window_api.ts` if components need it.
- Main-process changes need an app restart; renderer changes hot-reload under `npm run dev`.
- Drive the running app with `npm run -s agent -- …` (see `AGENTS.md`). `npm run dev` uses CDP
  port 9222 by default; pass `-- --remote-debugging-port=<port>` if another app holds it.
- After `update_exiftool.pl` at the repository root, refresh `assets/exiftool/` and
  `resources/nix/exiftool-config/` from `.resources/`.
- `npm run dev` stores its profile in `…/com.exifcleaner.ExifCleaner-dev`; `agent launch` and
  packaged builds use `…/com.exifcleaner.ExifCleaner`. Check the right `settings.json`.
